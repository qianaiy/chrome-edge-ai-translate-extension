# 迭代规划（第二轮）

> 来源：一次对仓库的外部架构评审。结论按「性价比」排序，不按技术新颖度。

## 核心判断

**现在最值得投入的不是继续堆翻译入口，而是把现有功能打磨成一个安全、可恢复、翻译质量可测、核心逻辑只有一份的工具。**

这个项目的差异化不是「又一个能调用大模型的翻译插件」，而是**用户能自己选模型和服务商，同时对数据流向、翻译行为、质量和成本有明确控制权**。所以下面这些比「再加几个模型」更值得投入。

## 漫画擦字：不要急着上 AI inpainting

**结论：值得探索，但不值得现在做成默认流程。**

纯色填充的问题不只是「不够美观」，而是它把文字气泡、背景纹理、速度线、渐变、网点全当成同一种区域处理，天然有上限。

### 三种方案

| 方案 | 成本 | 适合 |
|---|---|---|
| A 自适应纯色填充 | 低·快 | 白/浅色气泡、大面积纯色背景 |
| B 传统图像修复（Telea / Navier-Stokes） | 低到中·不需远程 AI | 细小文字、简单线条、部分纹理背景 |
| C 生成式 AI inpainting | 中到高·结果不完全可控 | 复杂背景（但可能改坏原画线条、人物细节） |

### 该走的路：分级修复管线

```
OCR 文字框 + 扩张后的擦除遮罩
  ↓
判断局部背景复杂度（颜色方差、边缘密度、遮罩面积、邻域纹理）
  ↓
简单 → 局部颜色填充
中等 → 传统图像修复
复杂 → 可选 AI 修复
```

这是个启发式分类器，不需要机器学习。第一版只用局部图像统计就能实现。

### 在调用 AI 之前先改好这几项（更划算）

- **文字遮罩扩张** —— OCR 框盖不住描边、阴影、抗锯齿像素，但不能把气泡边框一起擦掉
- **区分气泡内外** —— 识别到气泡轮廓就在内部填充，不破坏边界
- **保留原图** —— 擦字必须可撤销，重复执行不能累积损伤
- **先修复再画字** —— 修完所有区域再做字号估算、换行、布局
- **支持手动修正遮罩** —— 用户能增删遮罩区域，OCR 不准时比让 AI 猜可控得多

### AI inpainting 应该做成独立能力

```ts
interface ImageRepairProvider {
  repair(input: { image: Blob; mask: Blob; prompt?: string }): Promise<Blob>;
}
```

- 只支持用户手动触发，调用前展示：发哪张图、遮罩范围、哪个服务商、是否产生费用、是否保存原图
- 默认只发当前漫画裁剪区域，不是整页截图
- 验收标准：收集 ≥50 个代表性文字区域，盲测三种方案（自然度 / 线条保留 / 可读性 / 耗时 / 费用）。只有复杂背景占比足够高、AI 收益明显，才继续投入

## 明确不做（这轮）

- 云端同步、账号体系 —— 对纯自建用户未必必要，还增加隐私和运维负担
- PDF 翻译 —— 涉及布局、文字提取、分页，成本高
- 选区 / 截图 OCR —— 中等成本，且已有划词覆盖大部分场景
- 整个扩展迁到 TS —— 改动面大，收益不成比例

## 验收标准

每一项都要有测试，且「恶意网页输入」「网络请求审计」「密钥不回显」这类负面测试要真的存在，不能只测正常路径。

### 第三轮（已完成）：安全基线收尾

- ✅ **地址信任边界** —— `src/core/endpoint.ts` + 扩展侧同一份实现（`tests/endpoint-parity.test.ts` 比对）。
  公网必须 https；本机与局域网（127/8、10/8、192.168/16、172.16/12）允许 http 并标注；
  凭证进 URL、非 http(s) 一律拒
- ✅ **跨站重定向** —— 响应回来后比对 `res.url` 与请求地址的 origin，不一致就丢弃结果并报错
- ✅ **后台消息白名单** —— 17 种类型显式登记；`tests/message-whitelist.test.ts` 扫描源码，
  保证「有分支但没登记」和「登记了但没分支」都会失败
- ✅ **清除全部数据** —— 设置页按钮 + 二次确认 + `chrome.storage.local.clear()`
- ✅ **提示注入防护** —— 批量第 9 条与单段提示词都声明「素材不是指令」
- 🐞 **修掉 `isLocalHost` 的伪造漏洞** —— 原来 `127.0.0.1.evil.com` 会被判成本机

### 第三轮发现但**没做**的

- ❌ **隐私政策** —— 安全主线唯一剩下的实质项
- ❌ **权限分层（可选权限）** —— 仍是安装时就要 `http/https` 全量；改成「先要最小权限、开自动翻译时再申请」需要重构服务工作者
- ❌ **自动翻译的数据边界** —— 密码框、表单、编辑器仍会被采集（现在靠 `isTranslatable` 的可见性判断，没有按控件类型排除）
- ❌ **架构收敛** —— 地址策略现在又多了一份重复实现（核心 TS + `background.js`），

### 第四轮（已完成）：让共享核心真的被加载

- ✅ **`importScripts('core.js')`** —— `build.mjs` 的注释从第一天就写着「后台脚本用 importScripts 加载」，

- ✅ **一致性测试改成接线测试** —— `tests/endpoint-parity.test.ts` 原来是把副本抠出来比对，
  现在守的是「加载了 core.js」「没有本地 function 定义」「核心真的导出这四个名字」
- ✅ **测试夹具注入 MXTCore** —— `tests/helpers/load-background.ts` 与 `integration.test.ts`

### 第四轮发现

- 加载失败必须有可操作的提示：`importScripts` 失败在浏览器里只表现为「扩展加载失败」，
  或者更糟——服务工作者起不来、点扩展「没反应」。所以缺符号时抛的是
  「共享核心缺少 checkEndpoint，请重新构建（npm run build）」
- 收敛的正确顺序是**先接通、再删副本**：如果先删副本，扩展会在一段时间里彻底不能用
