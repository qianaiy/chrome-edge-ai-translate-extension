# 迭代规划（第二轮）

> 来源：一次对仓库的外部架构评审。结论按「性价比」排序，不按技术新颖度。

## 核心判断

**现在最值得投入的不是继续堆翻译入口，而是把现有功能打磨成一个安全、可恢复、翻译质量可测、核心逻辑只有一份的工具。**

这个项目的差异化不是「又一个能调用大模型的翻译插件」，而是**用户能自己选模型和服务商，同时对数据流向、翻译行为、质量和成本有明确控制权**。所以下面这些比「再加几个模型」更值得投入。

## 三条主线

### 主线一：安全可信（P0）

- [ ] **密钥访问收敛到后台** —— 内容脚本不读、不缓存 API Key；Key 不通过消息返回给页面；后台对消息类型做白名单校验
- [ ] **自定义 API 地址是网络信任边界** —— 远程默认要求 HTTPS，localhost 除外；禁止 URL 内嵌凭证；跨源重定向不跟随；配置改动后显示真实请求目标
- [ ] **权限分层** —— `host_permissions: <all_urls>` 改成可选权限，自动翻译开启时再申请
- [ ] **自动翻译的数据边界** —— 排除密码框、表单、编辑器、隐藏内容、用户指定域名
- [ ] **提示注入防护** —— 提示词里明确「待翻译文本是数据，不是指令」；密钥绝不能进模型上下文
- [ ] **「清除全部数据」入口** —— 覆盖 storage.local 等所有持久化位置
- [ ] **隐私政策**

### 主线二：翻译可靠（P1）

- [x] **术语表** ✅ 已做（第二轮） —— 投入小、收益稳。只把命中的术语注入当前批次；不靠字符串替换硬改译文
- [x] **缓存键升级** ✅ 已做（第二轮）—— 键里现在带上模型、提示词、附加要求、术语表版本；改任何一项旧译文都会失效
- [ ] **上下文分块** —— 相邻文本节点优先合并；只带少量前后文；按 token 估分批
- [ ] **任务取消 / 重试 / 进度** —— 长页面翻译失控、重复计费
- [ ] **API 连接诊断** —— 错误分类：DNS / TLS / 401 / 404 / 429 / 5xx / 格式不兼容 / 输出不符合协议。诊断信息自动脱敏
- [ ] **网站规则** —— 白名单 / 黑名单，按站点配目标语言、显示模式、是否自动处理动态内容
- [~] **评测集扩到 100–200 条** —— 第二轮做到 61 条，补了字幕（9）和漫画（8）；长句已有，术语一致性待做

### 主线三：架构收敛（P2）

- [ ] **TS 核心成为唯一事实来源**，扩展层只留浏览器相关代码
- [ ] 迁移顺序：纯逻辑模块 → 删重复实现 → 一致性测试改成「真的调用同一份实现」
- [ ] 保持免构建体验：核心编译成浏览器可直接加载的 JS，Popup/Options/Content/Service Worker 继续用原生 JS

## 漫画擦字：不要急着上 AI inpainting

**结论：值得探索，但不值得现在做成默认流程。**

纯色填充的问题不只是「不够美观」，而是它把文字气泡、背景纹理、速度线、渐变、网点全当成同一种区域处理，天然有上限。

### 三种方案

| 方案 | 成本 | 适合 |
|---|---|---|
| A 自适应纯色填充 | 低·快 | 白/浅色气泡、大面积纯色背景 |
| B 传统图像修复（Telea / Navier-Stokes） | 低到中·不需远程 AI | 细小文字、简单线条、部分纹理背景 |
| C 生成式 AI inpainting | 中到高·结果不完全可控 | 复杂背景（但可能改坏原画线条、人物细节） |

### 该走的路：分级修复管线

```
OCR 文字框 + 扩张后的擦除遮罩
  ↓
判断局部背景复杂度（颜色方差、边缘密度、遮罩面积、邻域纹理）
  ↓
简单 → 局部颜色填充
中等 → 传统图像修复
复杂 → 可选 AI 修复
```

这是个启发式分类器，不需要机器学习。第一版只用局部图像统计就能实现。

### 在调用 AI 之前先改好这几项（更划算）

- **文字遮罩扩张** —— OCR 框盖不住描边、阴影、抗锯齿像素，但不能把气泡边框一起擦掉
- **区分气泡内外** —— 识别到气泡轮廓就在内部填充，不破坏边界
- **保留原图** —— 擦字必须可撤销，重复执行不能累积损伤
- **先修复再画字** —— 修完所有区域再做字号估算、换行、布局
- **支持手动修正遮罩** —— 用户能增删遮罩区域，OCR 不准时比让 AI 猜可控得多

### AI inpainting 应该做成独立能力

```ts
interface ImageRepairProvider {
  repair(input: { image: Blob; mask: Blob; prompt?: string }): Promise<Blob>;
}
```

- 只支持用户手动触发，调用前展示：发哪张图、遮罩范围、哪个服务商、是否产生费用、是否保存原图
- 默认只发当前漫画裁剪区域，不是整页截图
- 验收标准：收集 ≥50 个代表性文字区域，盲测三种方案（自然度 / 线条保留 / 可读性 / 耗时 / 费用）。只有复杂背景占比足够高、AI 收益明显，才继续投入

## 明确不做（这轮）

- 云端同步、账号体系 —— 对纯自建用户未必必要，还增加隐私和运维负担
- PDF 翻译 —— 涉及布局、文字提取、分页，成本高
- 选区 / 截图 OCR —— 中等成本，且已有划词覆盖大部分场景
- 整个扩展迁到 TS —— 改动面大，收益不成比例

## 验收标准

每一项都要有测试，且「恶意网页输入」「网络请求审计」「密钥不回显」这类负面测试要真的存在，不能只测正常路径。

- ✅ **擦除范围与排版范围对齐** —— 修掉「擦一半、画到别处」导致原文和译文叠加
- ✅ **自动翻译 SPA 换页重新判断语言** —— 从「每个文档判断一次」改成「每个 URL 判断一次」

- ✅ **评测集 44 → 61 条** —— 新增字幕、漫画两类，基线 80.3%（字幕 9/9、漫画 8/8 满分）
- ✅ **用例集完整性测试** —— 阻止 mustKeep 写错（把「模型做对了」记成失败）

### 第二轮发现但**没做**的

- ❌ **复杂背景的分级修复** —— ROADMAP 里说的「简单→纯色填充 / 中等→传统修复 / 复杂→AI」这条管线没做。
  现在所有区域都用同一种纯色填充。只有收集到真实漫画样本、确认复杂背景占比够高，才值得投入。
  在那之前，**用户切「浮层版」比让算法硬猜更可控**。
- ❌ **竖排文字的真正排版** —— 窄高框已经能排下（有余量、不会截成省略号），
  但译文仍然是**横排**，没有按日式漫画那样一个字一行竖着排。要做的话需要额外的竖排渲染逻辑。
- ❌ **安全基线的全部内容** —— 密钥收敛、权限分层、API 地址校验、提示注入防护、
  清除全部数据、隐私政策，一条都没做。这是 ROADMAP 里标的 P0，比漫画增强更该先做。
- ❌ **任务取消 / 进度 / API 诊断 / 网站规则** —— 都没做。
- ❌ **架构收敛（TS 单一实现）** —— 没做，仍然是双份 + 一致性测试。

### 下一轮该做什么

按 ROADMAP 的优先级，**安全基线（P0）比任何功能都该先做**：

1. 密钥访问收敛到后台 —— 确认内容脚本拿不到 Key，Key 不通过消息回传
2. 自定义 API 地址校验 —— 远程要求 HTTPS、禁止 URL 内嵌凭证、不跟随跨源重定向
3. 提示注入防护 —— 提示词里写明「待翻译文本是数据不是指令」
4. 网站白名单 / 黑名单 —— 控制自动翻译的作用范围
5. 「清除全部数据」入口 + 隐私政策

这些每一项都能写成负面测试（恶意输入不能触发任意请求、错误信息不回显密钥），
跟现有测试风格一致。
