## 三、API Key 安全

### 3.1 修复清单

| # | 问题 | 位置 | 风险 |
| --- | --- | --- | --- |
| S1 | Gemini 的 Key 拼在查询串 `?key=…` | `src/core/protocol.ts` `buildRequest`、`src/extension/background.js` `buildRequest` 与 `listModelsOnce` | URL 会进浏览器历史、代理/网关访问日志、扩展调试日志，也可能随 `Referer` 外泄；日志一旦外传就无法回收 |
| S2 | `mxt:getSettings` 把完整设置（含 `apiKey`）返回给调用方 | `background.js` 消息处理 | 内容脚本跑在每一个被翻译的网页上，调用方多一处能拿到 Key 就多一处泄漏面 |
| S3 | 上游错误体里的 Key 原样显示给用户 | `callOnce` / `chat` 错误路径 | 多数厂商会在错误里回显 Key（`Incorrect API key provided: sk-…`），而这段文字会进弹窗和页面提示，用户截图分享即泄漏 |
| S4 | `401 / 403` 被当成「可重试」 | `RETRYABLE_STATUS` | 鉴权失败与协议形状无关，却会依次尝试三种协议：3 次无效请求、3 条重复报错把真实原因埋掉 |
| S5 | `host_permissions` / `content_scripts` 用 `<all_urls>` | `manifest.json` | 声明了 `file://`、`ftp://` 等从未真正注入过的范围，等于无谓扩大权限面 |

### 3.2 改法

- **S1**：改用 Gemini 官方支持的 `x-goog-api-key` 请求头；URL 只保留 `?alt=sse`（流式需要）。**仓库里本来就有正确写法** —— `background.js` 的 `transcribeAudio` 一直用请求头，这次是把另外两处对齐它。
- **S2**：响应改为 `{ ...settings, hasKey: boolean }`，`apiKey` 留在后台。需要 Key 的请求本来就全部由后台代发；设置页直接读 `chrome.storage`，不受影响。
- **S3**：新增 `redactSecrets(text, key)`（核心库与扩展各一份，逻辑一致）。用 `split/join` 而不是正则，避免 Key 里的 `. * +` 被当成元字符解释。`callOnce`、`chat` 聚合报错、流式分支统一过一遍。
- **S4**：`RETRYABLE_STATUS` 去掉 401/403，新增 `AUTH_STATUS`；命中时抛 `retryable = false, auth = true`，错误文案直接提示「Key 无效 / 没有该模型权限 / 额度不足，去设置页检查」。`400 / 404 / 405 / 422` 仍然重试（这些才可能是协议形状不对）。
- **S5**：收窄为 `http://*/*` + `https://*/*`。这不是拍脑袋——`background.js` 的 `injectable()` 本来就只在 `/^https?:/i.test(url)` 时注入，收窄只是让声明和实际行为一致。

### 3.3 证据

`tests/security-keys.test.ts`（30 条）覆盖每个入口，并额外守住「不能把功能修没了」：

- `★ URL 里不再出现 key=`、`★ key 放在 x-goog-api-key 请求头里`、流式请求仍带 `alt=sse`
- 扩展侧 `buildRequest` 与核心库一致；拉模型列表也不拼查询串
- `redactSecrets`：多次出现全替换、Key 为空时不动、不误伤其他文本、Key 含特殊字符也照常替换
- `★ 401 只尝试一次协议，不跑满三种`、`★ 403 也只尝试一次`、`★ 上游把 key 回显在错误体里时最终报错不含 key`
- `404` / `400` **仍然**回退（防止矫枉过正）
- `★ 返回里没有 apiKey 字段`、`★ 用 hasKey 布尔值告知配没配`、`设置页自己做翻译时后台仍然拿得到 Key`
- manifest：`★` 三条权限断言 + `仍然保留 manifest v3 与最小权限集`

浏览器侧另有一条**运行时**断言：回归套件记录所有经过本地服务的请求 URL，断言 `API Key 未出现在任何请求 URL 中`（6 个请求）。

## 四、分段标记完整性

批量翻译的协议是让模型按 `<<<1>>>…<<<2>>>…` 分段返回。原来的解析有两个洞，都属于「错了但不报错」——最坏的一类。

### 4.1 `parseMarked`：重复编号静默覆盖

| 模型返回 | 旧行为 | 新行为 |
| --- | --- | --- |
| `<<<1>>>甲<<<2>>>乙` | `['甲','乙']` | 不变 |
| `<<<1>>>甲<<<1>>>乙`（count=2） | `['乙', null]` —— 第 2 段是 null 会触发重试，但**第 1 段悄悄变成了「乙」**，用户看到的是一段错位译文，且没有任何迹象 | `[null, null]`，整批按段重试 |

旧实现是「后写覆盖前写」，覆盖之后该位置非 null，于是重试逻辑认为这段成功了。新实现先记录首次出现，再标记重复项，重复项一律留 null 交给重试。

### 4.2 `splitInlineMarks`：重复 `{{n}}` 静默覆盖

逐条重译用 `{{1}}…{{2}}…` 保序。旧实现只检查「数量对不对」和「编号是否越界」，`{{1}}甲{{1}}乙`（count=2）数量对得上、编号也合法，于是第一段被覆盖成「乙」、第二段是空串。

**这条以前被测试当成正确行为固定下来了**：`tests/inline-marks.test.ts` 原来断言 `['乙', '']`。这次改成返回 `null`（退回逐条重译），并把那条测试的期望一并纠正——测试锁住错误行为，比没有测试更糟。

### 4.3 证据

`tests/segments-integrity.test.ts`（21 条），分四组：

- 重复编号 → 该位 `null`；`★ 被覆盖的内容不会冒充成该段的译文`
- 正常路径不能被改坏：编号齐全、乱序按编号落位、缺一段、越界忽略、无标记、`count=0`
- `parseMarked · 结果只能来自本段或 null`：参数化跑一批输入，断言「每一段要么是本段原文翻译，要么是 null，绝不串味」
- 扩展与核心一致：`background.js` 的 `parseMarked` 对重复编号同样返回 null

核心库（TS）与扩展（JS）是两份实现，本轮同步修改并双向对齐（沿用仓库原有的 `tests/inline-marks.test.ts` 抠函数比对的做法）。

## 五、回归中发现的额外缺陷（重要）

浏览器回归第一版跑出 5 项失败，其中 4 项是**套件自己写错了**（就绪探针查了不存在的字段、还原后拿「加过动态内容之前的快照」做整页比对、SPA 用例在 DOM 被替换后才去找旧中文），已修正为更准确的断言。剩下 1 项是**产品的真实缺陷**：

### 框架改写原文后，旧译文不被作废

- **现象**：React 之类的框架把 `<p>` 的文字改掉（列表刷新、倒计时、路由局部更新），扩展插进去的译文节点还留着，页面上就出现「新的英文原文 + 一句和它无关的旧中文译文」。
- **根因 1**：`invalidateIfReverted()` 第一行是 `if (!rec || !rec.swapped) return false;`，`rec.swapped` 只有「译文-only 模式」才会置真。**默认的双语模式永远不走这段逻辑。**
- **根因 2**：作废调用原先放在 `collectTextContainers()` 里、且在收集**之后**。即便作废成功，这一轮区块列表已经生成、这个块已被跳过，要等下一轮才有机会补翻——而下一轮往往永远不会来（没有新的 DOM 变动就没有下一次观察回调）。
- **改法**：
  1. 把作废循环搬到 `collectBlocks()` 最前面，在收集之前执行，同一轮就能重新收集、重新翻译。
  2. 判定条件分两种：`rec.swapped` 为真时看「原文有没有被顶回来」；为假（双语模式）时看「原文有没有被改成别的内容」。
  3. 跳过 `rec.parts`（按文本节点换的块），这类块的 `ownText` 本来就被译文覆盖，拿它判断会每轮自我作废、无限重翻。
  4. 作废时顺手清掉 `data-mxt-out` ——不清的话该块被 CSS 藏起来，重翻也看不见。
- **守护**：回归用例「框架重渲染后重新翻译」+ 还原用例「恢复后各块文字回到原文 / 不残留注入节点与标记」。

## 六、共享核心与扩展的重复实现分析（第 5 组任务，本轮只分析不重构）

### 6.1 现状

`src/core/`（TypeScript，有单测）与 `src/extension/background.js`（纯 JS，MV3 后台）存在成对的重复实现：

| 逻辑 | 核心库 | 扩展 |
| --- | --- | --- |
| 厂商表、base 归一化、协议猜测与顺序 | `provider.ts` | `background.js` |
| 三种协议的请求构造与响应解析 | `protocol.ts` | `background.js` |
| 系统提示词、`parseMarked`、`splitInlineMarks` | `prompt.ts` | `background.js` / `content.js` |
| 术语表选择与一致性检查 | `cache.ts` | `background.js` |
| 配置体检规则 | `provider.ts` | `background.js` |
| 字幕解析 | `subtitle.ts` | `content/subtitle.js` |

一致性靠测试守着：`tests/integration.test.ts`、`tests/glossary-consistency.test.ts`、`tests/inline-marks.test.ts`、`tests/extension-syntax.test.ts` 会把扩展里的函数抠出来跑同一批输入。

### 6.2 一个值得记录的发现

`scripts/build.mjs` 会把 `src/core` 打成 `dist/core.js`（全局 `MXTCore`），但**运行时没有任何东西加载它**：`manifest.json` 没声明、`background.js` 里 `MXTCore` 出现 0 次、`dist/background.js` 也没有 `importScripts`。

也就是说，目前「共享核心」的角色是**测试用的事实来源**，而不是运行时依赖；真正跑在浏览器里的是 `background.js` 里那套复制品。这解释了为什么两边会慢慢漂移，也说明重构的收益是真实的。

### 6.3 建议（不在本轮执行）

下一轮单独开分支，按「一次只换一个模块」推进：先把纯函数模块（`prompt.ts` 的解析、`cache.ts` 的术语表）改为从 `MXTCore` 取，用 `importScripts('core.js')` 接上；每换一个跑一次全量单测 + 浏览器回归。**不做一次性大重构**——本轮的任务约束明确禁止，而且现有测试是按「两份实现互相校验」写的，先破坏这个结构会同时失去护栏。

## 七、浏览器回归套件

`scripts/browser-regress.mjs`（新增，约 550 行），`npm run regress` / `regress:edge` / `regress:all`。

与已有的 `smoke.mjs` 的区别：smoke 验「装得上、能跑」；regress 验**行为正确**——它起一个本地 HTTP 服务当假翻译 API，把真实构建装进浏览器，用页面里的真实 DOM 和后台的真实消息通道跑完整流程。

| # | 用例 | 守的东西 |
| --- | --- | --- |
| 1 | 内容脚本就绪 | `mxt:ping` 的 `ready` 字段（不是 status 猜的） |
| 2 | 整页翻译产生译文 | 批量翻译走通 |
| 3 | 译文进入页面 | 译文真的落到 DOM |
| 4 | 双语对照保留原文 | 英文原文没被吃掉 |
| 5 | 译文没有漏出编号标记 | `<<<` / `>>>` 不泄漏到页面 |
| 6 | 第一段编号正确 | 分段映射没错位 |
| 7 | 动态菜单项被自动补翻 | MutationObserver 补翻后插入节点 |
| 8 | 无限滚动追加的内容被自动补翻 | 批量追加 |
| 9 | 框架重渲染后重新翻译 | 第五节修的那个缺陷 |
| 10 | API Key 未出现在任何请求 URL 中 | S1 的运行时铁证 |
| 11 | 一键恢复原文 | 还原后无译文残留 |
| 12 | 恢复后各块文字回到原文 | 逐块比对（不是整页字符串，避免被动态内容干扰） |
| 13 | 恢复后不残留注入节点与标记 | `.mxt-trans` / `mxt-orig` / `mxt-swapped` / `data-mxt-out` 全清零 |
| 14 | SPA 页面内容脚本就绪 | 换页后仍在 |
| 15 | SPA 换页后自动翻译外文页面 | 路由变化后自己发现并翻 |
| 16 | SPA 换页前中文页没被误翻 | 用页面在换页前自己拍下的快照判断（换页后 DOM 已被替换，事后没法看） |

结果：**Chrome 16/16、Edge 16/16**。

### 顺带修的仓库卫生问题

`lint:secrets` 本轮报了一次警：`_bili-handoff/` 目录里是本机工具产出的会话转写，含 GitHub token（该目录未被跟踪，但扫描器做了全盘遍历）。两处改动：

1. `.gitignore` 增加 `_bili-handoff/`（这类文件永远不该进仓库）。
2. `scripts/secret-scan.mjs` 改为只扫「可能被提交的文件」（`git ls-files --cached --others --exclude-standard`），与「什么会进仓库」对齐；显式传目录参数时仍走全盘遍历。同时保留负向验证：故意放一个 `sk-` 开头的假 Key，扫描器仍然报错退出 1。

另有一处不能靠「扫描器加例外」解决：回归套件需要一个 `sk-` 形状的探针密钥来证明「Key 不进 URL」。处理方式是**在运行时用字符串拼接出来**，源码里不出现任何密钥形状的字面量——扫描规则保持严格，比给它开口子安全。
