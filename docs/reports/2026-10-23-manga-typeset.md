# 漫画嵌字故障专项修复

日期：2026-10-23
分支：`fix/manga-typesetting`（从 `feature/p0-baseline` 切出，未合并 main）
提交：见本文件末

## 一、真正的故障根因

现象是「OCR 和翻译都成功，但译文写不进漫画气泡」。实测后确认根因不在 OCR，也不在翻译模型，而是**渲染层的坐标系用错了容器**。

### 证据

用 `scripts/manga-typeset-check.mjs` 在真实浏览器里装载构建产物，跑一张 800×1200 的合成漫画页，DOM 实测：

```
图片渲染盒：{left:60, top:48, width:420, height:630, nw:800, nh:1200, objectFit:"fill"}
父容器    ：{left:0,  top:0,  width:1264, height:798, position:"relative"}
擦字图层  ：{left:0,  top:0,  width:1264, height:798}   ← 贴的是父容器
```

`src/extension/content/comic.js` 的 `paintInpainted` 当时是这样写的：

```js
left: '0', top: '0', width: '100%', height: '100%', objectFit: 'contain'
```

父容器是整块版面（1264×798），图片盒只有 420×630 且相对容器偏移 (60, 48)。
于是整张擦好的图被按 `contain` 缩放并居中，跟用户看到的图片完全错位——**气泡里的字其实画对了，但整张图被搬到别处显示**，肉眼看就是「译文没进气泡」。

这也解释了为什么之前 MangaDex 实测会「通过」：那条断言只检查了「有没有生成擦字图层」，没检查它和图片是否重合。

### 另外两个次级问题

2. 浮层版的字号写死 `15px`，宽度用「汉字≈1 字号宽」粗估。长译文会溢出气泡，短译文又偏小。
3. 没有竖排、没有中文标点禁则、装不下时也没有任何提示——字被 `overflow:hidden` 直接裁掉，用户看到的是「少半句」。

## 二、最小范围修复

只改 `src/extension/content/comic.js`，没有重写插件，没有替换翻译引擎。

### 1. 覆盖层定位（根因修复）

- 新增 `placeOver(img, el)`：按 `getBoundingClientRect()` 的差值把覆盖层精确压在图片盒上，`object-fit: fill`。
- 新增 `trackOverlay` / `repositionOverlays`：`resize` + `ResizeObserver` + 图片 `load` 时重算，缩放和懒加载都不会错位。

### 2. 气泡内排版

- `textWidth()`：用 canvas `measureText` 真实测量，替掉按字数估算。
- `layoutH()`：从大字号往下搜，找「整段放得下」的最大字号。
- `wrapText()`：按实测宽度折行，带 CJK 行首禁则（`、。，」` 不能起行）与行尾禁则（`（「` 不能收行）。
- `layoutV()` / `isVerticalBox()`：窄高框或译文含假名时走 `writing-mode: vertical-rl`。
- 装不下时：橙色虚线框 + `contenteditable`，**不丢字**，用户可以就地改短。
- 点击气泡切换原文/译文。

### 3. Debug Mode

面板新增「调试」按钮，不重新请求接口，只改显示：

- 图片原始尺寸 / 显示尺寸 / 显示坐标
- 识别到的文字块数
- 每条：编号、框尺寸（CSS px）、字号、行数、横排还是竖排、是否溢出
- 覆盖层描边：绿色=正常，红色=溢出

### 像素级验证（关键）

只看几何位置不够——位置对了但画布上没字，同样是坏的。所以直接把擦字图层的 dataURL 解码，统计每个气泡内部的深色像素比例：

```
box [8,5,45,18]   inkRatio 0.226  ringRatio 1.0
box [52,22,92,36] inkRatio 0.211  ringRatio 1.0
box [20,45,70,62] inkRatio 0.174  ringRatio 1.0
```

- `inkRatio > 0.01` → 气泡里确实有新画的字（不是空白）。

## 六、没做到 / 跑不了的部分

必须说清楚，不能拿「全部通过」糊过去：

1. **气泡分割没有实现**。任务书要求「单独保存气泡区域和文字区域」，目前模型只返回文字区，气泡框就是文字框。要做真正的 bubbleBox，需要在 OCR 之后加一步轮廓/连通域分析。现在的不规则气泡只能靠安全边距近似。
2. **复杂背景仍是纯色擦除**。渐变、纹理、速度线会被填成一块颜色。分级修复（简单→填充、中等→传统修复、复杂→AI）仍未做，AI 修复接口也没接。
3. **`object-fit: fill` 假定图片没有额外裁切**。如果目标站用 `object-fit: cover` 裁切原图，覆盖层会跟着裁切位置错。这种情况尚未处理。
4. **我看不了截图**。当前会话使用的模型（`sn-deepseek-v4-1-flash-1017`）不接受图像输入，`read_image` 直接报「does not declare image input」。所以「修复前后效果」我只能给数字和几何量，**最终好看不好看需要你打开 `artifacts/manga-typeset/` 自己看一眼**。
5. 竖排只做了「按列排、自右向左」，没做日式标点竖排变形（`。`→ 右上角小圈）和英数字竖排正立这类细节。

## 七、下一步建议

按性价比：

1. **先让别人眼睛确认**：打开 5 张截图，确认普通白底气泡是否「能看」。
2. 气泡分割（连通域 + 椭圆拟合）：有了它，安全边距和溢出判断都会准很多。
3. 文本区域擦除改成「按掩码擦」而不是「按矩形擦」，减少吃边风险。
4. 最后再考虑分级背景修复与 AI 修复接口。

## 第二轮：气泡区域与文字区域分离（commit 8cda12b）

### 之前的状态
模型只给一个文字框，气泡框 = 文字框。后果有两个方向：框比气泡大时擦除会吃掉描边，
框比气泡小时排版可用区算小、长译文被过早缩字号。

### 本次做法
`src/core/inpaint.ts` 新增 `findBubbleRegion` / `eraseBubble`：

1. **气泡底色 = 框内像素的中位色**。原先用框外一圈估计，结果是「页面底色」——
   照它判定可通行区域，气泡内部反被判成不可通行，整页底色成了候选连通域，一定认不出。
2. **连通域并集**。字、拟声字、速度线会把气泡内部切成好几块，只取最大那块会框不住文字，
   擦也只擦一块、原文留半截。改为把所有和文字框有交集的连通域并起来判范围，擦除时逐块擦。
3. **边界要闭合**。连通域把整个搜索窗口撑满，说明窗口里没有闭合边界（字直接压在画面上），
   判为非气泡。
4. **正交凸包填洞**。字迹本身不是气泡底色，逐行逐列各补一次，洞被填上、形状仍是气泡的。
5. **狭隘阈值**。气泡内部天然比框小一圈（描边、圆角），原先 95% 的阈值在窄高框上直接判死
   （实测 72px 宽的框，内部只有 66px）。改为 75%~260% 区间。
6. 认不出来就 `rectFallback`，不假装认到了。

### 接线
`background.js` 注入漫画脚本时一并注入 `core.js`，`comic.js` 优先走气泡掩码；
`core.ts` 导出新 API；Debug Mode 增加「气泡识别 N/M」与规划明细，方便现场判断。

### 过程中踩的坑
