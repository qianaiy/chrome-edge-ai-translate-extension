# 真实漫画图片嵌字验证与修正能力

日期：2026-10-24 ｜ 分支：`fix/manga-typeset-real` ｜ 基线提交：`fe12927`

## 一、结论先说

合成页上的 20/20 曾经给人一种「已经好了」的错觉。换成真实几何的图以后，问题立刻现形：
**排版数字是 `undefined`、矩形兜底坐标是 `NaN`、模型坐标有时按 0-1000 给而不是百分比**。
这三个都不是「效果不够好」，而是「算出来的数字根本不是数字」。

现在：

| 项目 | 结果 |
| --- | --- |
| 单测 | 604 tests / 33 files 全过（基线 571） |
| 合成页嵌字检查 | Chrome 20/20、Edge 20/20（原 18 项，新增 2 项） |
| 真实样本嵌字检查 | 3 张图 × 2 浏览器 = 6 次，全部 20/20 |
| 真实样本几何指标 | 嵌字成功率 90.9%–100%、译文溢出率 0%、错误匹配率 0% |
| 网页翻译回归 | Chrome 22/22、Edge 22/22 |

## 二、真实样本是怎么来的（为什么不是网图）

任务要求「使用有权处理的真实漫画图片」。我没有用任何第三方漫画页的图——那些图不在我
可以处置的范围里，进仓库还会带来版权问题。

做法是 `scripts/make-real-samples.py` 用 Pillow 生成三张**按真实难点设计**的图，并把真值
（每处文字的位置、原文、参考译文）写进 `artifacts/real-samples/manifest.json`：

| 样本 | 尺寸 | 文字区 | 覆盖的真实难点 |
| --- | --- | --- | --- |
| `jp-vertical` | 800×1200 | 5 | 两层竖排日文气泡、竖排小字、满屏网点背景、深浅对比 |
| `jp-burst` | 800×1000 | 3 | 爆炸气泡（锯齿边）、圆角气泡、拟声词、锥形速度线 |
| `kr-strip` | 900×1600 | 3 | 宽横幅气泡、不规则气泡、长文本气泡、韩文 |

关键在于：**图是我们自己的，但坐标是模型自己给的**。`scripts/manga-real-check.mjs` 把图真的
发给视觉模型，记录它返回的框，再拿真值量。没有「手写正确坐标冒充检测成功」这回事——第
一轮测出 63.6% 就是这么暴露的。

样本图与模型原始回答都已入库（`artifacts/real-samples/`，约 110 KB），任何人可以重跑复核。

## 四、修掉的四个真缺陷（都是先红后绿）

### 1. 坐标系统混用（影响最大）

实测对照（同一批模型回答，按四种解释分别算真值覆盖率）：

| 解释 | jp-vertical | jp-burst | kr-strip |
| --- | --- | --- | --- |
| percent（原假设） | **5/5，平均 0.87** | 1/3 | 0/3，平均 0.00 |
| pixels | 0/5 | 0/3 | 0/3，平均 0.05 |
| 0-1000 归一化 | 0/5 | 0/3 | **3/3，平均 0.88** |

结论：**同一个模型在不同调用里会用不同约定**。原先「数值在图片尺寸内就按像素算」的规则
把 kr-strip 判成 pixels，覆盖率 0.05——等于把整页字画到画面外。

新增 `src/core/vision-box.ts`：`detectBoxSystem` 按 100 / 1000 两条线判定
（≤100 百分比、≤1000 按 0-1000、>1000 且落在图内才算像素），另有 `sanitizeVisionItems`
做规范化、夹取、去重，`mergeDuplicateBoxes` 合并模型把同一句拆成两块的重复框。
`translateImage` 现在把图片宽高一起传给后台，不再靠猜。

### 2. 排版字段读出 `undefined`

`state.layouts` 里的字号来自 `layoutH/layoutV` 的返回值，字段名是 `size`。界面读的是
`fit.size`（对的），但调试输出里出现过 `undefinedpx`——说明这条链路曾经被改坏过而没人发现，
因为**没有任何断言检查「数字是不是数字」**。

已加断言：Debug 文本里出现 `undefined` 或 `NaN` 直接失败。

### 3. 矩形兜底坐标是 `NaN`

`adaptivePad(box, w, h)` 需要 `{x1,y1,x2,y2}`，调用点传的是 `{box:[...]}`。取到
`undefined`，减出来 `NaN`，于是兜底矩形的四个坐标全是 `NaN`。

为什么一直没发现：合成页四个气泡全被识别成气泡，**这条路径一次都没走到**。真实图上 5 条
有 4 条走这条路——等于擦字和排版同时失效，而且没有任何报错。

### 4. `fitText` 没有溢出判定

两个副本（`src/core/inpaint.ts` 与 `content/comic.js`）都只返回 `shrunk`，界面却在读
`fit.overflow`。结果是：**译文被截断成省略号，用户看不到任何提示**。现在补上
`overflow` / `clamped`，并区分「横向超宽」「纵向超高」「被截断」三种成因。

## 五、人工修正（只在用户操作时改页面）

| 手势 | 作用 |
| --- | --- |
| 单击 | 选中一条译文（蓝框） |
| 双击 | 进入编辑，改完 Enter 提交、Esc 放弃，改完自动重新排版 |
| 拖动 | 移动译文位置，位置会换算回百分比写回数据 |
| 右键 | 看原文 / 看译文 |
| Alt + 拖动 | 在图上重画一个框，作为选中那条的新气泡区域 |
| `A-` / `A+` | 调字号 |
| 自动适配 | 按当前框重排（会覆盖手动字号） |
| 导出 | 把当前图连同译文存成 PNG |

溢出时自动给虚线黄框和提示文案。原图始终保留：擦字是画在覆盖层上的副本，导出才落盘。

## 六、真实样本指标（`npm run real`，需视觉模型）

最近一次：

```
真值 11 条，模型原始 11 条，去重后 11 条
嵌字成功率（真值文字区被框覆盖 ≥0.6）   90.9%  10/11
框超出气泡率（>2%）                    20.0%  2/10
译文溢出率（排完仍装不下框）            0.0%   0/10
错误匹配率（框对但文字对不上）          0.0%   0/10
框面积离谱（>3 倍或 <0.25 倍气泡）      3/10
多余框占比                              9.1%   1/11
```

上一轮同一脚本跑出的是 100%（11/11），再次说明模型输出有随机性。两个数都记下来，不挑好看的。

**「框面积离谱 3/10」这条必须单独说**：模型有时把整个气泡而不是文字行当作文本区，框给得很大。
框大 → 真值当然被「覆盖」，覆盖率就显得好看。所以我加了面积比值这一项来对冲这种假成功。

| --- | --- | --- | --- | --- |

## 七、已知限制（不粉饰）

1. **真实图上气泡识别率低**（1/5、2/3、2/3）。参数是在合成页上调的：真实网点的边缘梯度、
   开口气泡、字压在画面上，都会让「闭合连通域」这一判据失效。失效后老实退回矩形。
2. **退回矩形会擦到一点画面**（最大 26.5 的像素差）。字直接压在背景上时这是必然的——
   没有气泡边界可依。缓解办法是切「浮层版」，不改原图。
3. **框比气泡大**时擦除范围也跟着大，会把气泡外的画面一起擦掉（见面积比值 3/10）。
4. **竖排仍按横排渲染**中文译文。窄高框能排下，但没有日式竖排的列序。
5. **我看不到截图**——本轮所有效果判断都来自像素测量与几何测量，不是「看着不错」。
   这也意味着配色、字体美观度这类问题只能靠你目视。
6. 样本是脚本生成的，不是真的第三方漫画页面。它能覆盖几何与文字难点，但覆盖不了
   真实站点的懒加载、画布渲染、分片图这类工程问题（那些在 `scripts/manga-live-check.mjs` 里）。
